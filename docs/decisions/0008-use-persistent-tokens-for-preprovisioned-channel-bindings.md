# ADR 0008: Use persistent tokens for pre-provisioned channel bindings

- Status: Accepted
- Date: 2026-07-30

## Context

Channel sender bindings are pre-provisioned and stored in the database so terminal clients can authenticate without manual token entry. These bindings are generated by the seed flow and then reused by channel terminals.

During this session, reseeded bindings worked only after the token generator was switched from `GenerateToken(entity, false)` to `GenerateToken(entity, true)`. The non-persistent path produced JWTs with the short `Identity:Token:TimeoutMinutes` lifetime (30 minutes by default), which expired quickly and caused the Gateway to resolve requests through the anonymous/guest fallback path.

## Decision

Use persistent tokens for pre-provisioned channel bindings:

- Seed/provisioning flows should call `GenerateToken(..., true)` for stored binding tokens.
- Keep the short-lived token path only for ephemeral or session-bound scenarios.

## Consequences

Positive:

- Pre-provisioned channel bindings remain usable across time and avoid surprise expiration during normal use.
- Gateway requests resolve through the intended binding instead of falling back to anonymous/guest when a stored token is still expected to work.

Tradeoffs:

- Persistent tokens must be treated as durable secrets and regenerated if the signing key changes.
- Operators still need a fixed `Identity:Token:SecretKey` for restart durability.

## Debugging Pattern

If a request unexpectedly falls back to anonymous after seeding:

1. Check whether the stored binding token is expired.
2. Confirm the seed path used `GenerateToken(..., true)` for the stored token.
3. Verify `Identity:Token:SecretKey` is fixed across restarts.

- OpenCode session `ses_05062dc27ffepsLooAb5paduHx`, `2026-07-30`:
